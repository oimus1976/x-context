# SPEC-0001 — x-context MVP

- **Status:** Proposed
- **Date recorded:** 2026-09-09
- **Related:** Issue #1
- **Scope:** Specification only; no product implementation in this work item

## 1. Purpose

x-context provides a read-only, official-API-based way to obtain X content for local tooling and AI-assisted analysis without relying on browser scraping, internal GraphQL endpoints, or cookie automation.

The MVP establishes three use cases:

- **UC-001:** Read an arbitrary X post from a supported status URL.
- **UC-002:** Read the authenticated user's bookmarks.
- **UC-003:** Read the authenticated user's liked posts.

## 2. Design principles

1. The official X API is the only runtime data-access provider in the MVP.
2. Authentication scopes are read-only.
3. Credentials and private activity data are handled as sensitive local data.
4. JSON is the canonical machine-readable output contract.
5. Failure is explicit. Unsupported or unauthorized conditions do not trigger unofficial fallback behavior.
6. Material behavior changes follow: requirement -> acceptance criteria -> test -> implementation.

## 3. Functional requirements

### FR-001 — Extract post ID from supported status URLs

The system shall extract a numeric post ID from supported X/Twitter status URLs.

#### Accepted URL families

- `https://x.com/{user}/status/{numeric_id}`
- `https://www.x.com/{user}/status/{numeric_id}`
- `https://twitter.com/{user}/status/{numeric_id}`
- `https://www.twitter.com/{user}/status/{numeric_id}`

Query strings and fragments may be present and must not alter the extracted status ID.

#### Acceptance criteria

- **AC-FR001-01:** A valid supported URL returns the exact numeric status ID.
- **AC-FR001-02:** Query parameters and fragments are ignored for ID extraction.
- **AC-FR001-03:** Non-X/Twitter hosts are rejected.
- **AC-FR001-04:** URLs without a numeric `/status/{id}` segment are rejected.
- **AC-FR001-05:** Rejection is explicit and does not make a network request.

### FR-002 — Fetch an arbitrary post through the official X API

Given a valid post ID, the system shall retrieve the post through the documented official X API.

#### Acceptance criteria

- **AC-FR002-01:** The request uses only the official X API provider implementation.
- **AC-FR002-02:** A successful response is normalized to the canonical output model.
- **AC-FR002-03:** 401/403 authentication or authorization failures are reported as explicit failures.
- **AC-FR002-04:** 404 or equivalent unavailable-post conditions are reported distinctly from authentication failures.
- **AC-FR002-05:** 429/rate-limit conditions are reported distinctly and expose safe diagnostic metadata when available.
- **AC-FR002-06:** No failure path invokes scraping, browser automation, cookie access, or internal GraphQL.

### FR-003 — Fetch authenticated user's bookmarks

The system shall retrieve bookmarks for the authenticated X user using the official bookmarks endpoint available to that user's authorization context.

#### Acceptance criteria

- **AC-FR003-01:** The endpoint is called only with read-capable user authorization required by the official API.
- **AC-FR003-02:** Results are normalized to the canonical output model.
- **AC-FR003-03:** Pagination is represented explicitly; the implementation must not silently truncate while claiming completeness.
- **AC-FR003-04:** Bookmark payloads are not persisted by default.
- **AC-FR003-05:** Missing scope/permission is an explicit failure and does not trigger fallback access.

### FR-004 — Fetch authenticated user's liked posts

The system shall retrieve posts liked by the authenticated X user using the official API.

#### Acceptance criteria

- **AC-FR004-01:** The endpoint is called only with the read-capable user authorization required by the official API.
- **AC-FR004-02:** Results are normalized to the canonical output model.
- **AC-FR004-03:** Pagination is represented explicitly; the implementation must not silently truncate while claiming completeness.
- **AC-FR004-04:** Like-history payloads are not persisted by default.
- **AC-FR004-05:** Missing scope/permission is an explicit failure and does not trigger fallback access.

### FR-005 — Canonical JSON output

The MVP shall expose one canonical normalized JSON model for successful reads.

Minimum top-level contract:

```json
{
  "schema_version": "1",
  "source": "x",
  "operation": "read|bookmarks|likes",
  "items": [],
  "page": {
    "next_token": null,
    "complete": true
  }
}
```

Each item representing a post must support, when available from the official response and requested fields:

- post ID;
- text;
- author identity sufficient to represent X user ID and username when resolved;
- created-at timestamp when resolved;
- canonical X URL derived from normalized identifiers;
- referenced/quoted post metadata when included by the provider contract;
- media/link references when included by the provider contract.

Absence of an optional expansion must not be misrepresented as evidence that the underlying post has no such data.

#### Acceptance criteria

- **AC-FR005-01:** All three MVP operations use `schema_version = "1"`.
- **AC-FR005-02:** Output distinguishes absent/unrequested optional data from known-empty data where material.
- **AC-FR005-03:** Output contains no access token, refresh token, client secret, authorization header, cookie, or equivalent credential material.
- **AC-FR005-04:** Provider-specific response details do not become the public CLI contract unless explicitly specified.

### FR-006 — CLI contract

The MVP shall expose these logical commands:

```text
x-context read <x-status-url>
x-context bookmarks
x-context likes
```

The exact Python packaging/entry-point mechanism is an implementation decision, but the observable command behavior shall preserve this logical interface.

#### Acceptance criteria

- **AC-FR006-01:** Successful commands emit canonical JSON to standard output by default.
- **AC-FR006-02:** Human-readable diagnostics go to standard error and do not corrupt JSON output.
- **AC-FR006-03:** Failures produce a non-zero exit code.
- **AC-FR006-04:** Invalid local input is distinguishable from authentication, provider, rate-limit, and unavailable-resource failures.
- **AC-FR006-05:** Normal command output does not include credentials or full authorization material.

## 4. Non-functional and safety requirements

### NFR-001 — Official X API only

Runtime acquisition of X data in the MVP must use documented official X API interfaces only.

**Forbidden MVP fallback paths:**

- HTML scraping;
- browser automation;
- reuse of browser cookies;
- undocumented/internal GraphQL endpoints;
- third-party mirrors or scraping proxies presented as equivalent authority.

A future provider may be proposed only by changing this specification and the relevant ADR before implementation.

### NFR-002 — Read-only authorization boundary

The MVP must request only scopes/permissions needed for read operations. Write scopes for posting, deleting, liking, bookmarking, following, DM operations, or equivalent mutations are out of scope.

The implementation must not expose a write operation even if a supplied credential happens to possess broader authority.

### NFR-003 — Credential protection

Credentials must not be committed to Git, embedded in fixtures, emitted in logs, included in exception text intentionally, or written to normal command output.

Repository examples and tests must use obvious fake values.

### NFR-004 — Fail closed on unofficial fallback

If the official API cannot satisfy an operation, x-context must return an explicit error. It must not automatically switch to an unofficial acquisition path.

### NFR-005 — Usage/cost observability

The system should expose enough non-secret metadata to diagnose unexpected API consumption, such as operation name, request count, returned item count, pagination state, and safe provider rate-limit metadata when available.

Observability must not require logging private payload bodies.

### NFR-006 — Private activity data handling

Bookmarks and likes are treated as private user activity data even when the referenced posts are public.

Default behavior is process-and-return, not persist. Any future local persistence feature requires a specification change defining storage location, retention, deletion, and export behavior.

## 5. Error model

The implementation must provide stable error categories sufficient for callers/tests to distinguish at least:

- `invalid_input`
- `authentication_failed`
- `authorization_failed`
- `resource_unavailable`
- `rate_limited`
- `provider_error`
- `configuration_error`

Provider-specific status codes may be recorded as diagnostic metadata, but callers must not need to parse arbitrary provider text to determine the category.

## 6. Security and privacy boundary

The MVP can read public posts by ID and authenticated-user activity permitted by the credential. It has no product-level mutation authority.

The following data must be considered sensitive in logs/tests/reports:

- access tokens, refresh tokens, client credentials;
- authorization headers;
- authenticated bookmark/like collections;
- raw private provider responses that include user activity not needed for a test artifact.

Real-boundary smoke evidence should record success/failure metadata without publishing private payload contents.

## 7. Out of scope for SPEC-0001

- posting, deleting, liking, bookmarking, following, blocking, muting, or any other X write operation;
- direct-message access;
- mentions, lists, followers/following synchronization;
- background monitoring or scheduled ingestion;
- Obsidian/Markdown export;
- LLM summarization, classification, or enrichment;
- unofficial GraphQL, browser-cookie, scraping, or mirror providers;
- long-term persistence of X activity data.

## 8. Traceability contract

Every requirement implemented under this specification must have a corresponding acceptance-test mapping in `docs/TEST_MATRIX.md`.

A material behavioral change follows this order:

1. update the requirement/acceptance criteria;
2. update the test matrix and tests;
3. update implementation;
4. record validation evidence.

Implementation-first changes that are later backfilled into the specification are not the normal development path.

## 9. MVP implementation gate

Product implementation may begin only after the spec PR establishes:

- accepted MVP scope;
- accepted provider/authentication boundaries;
- accepted canonical output/error contracts;
- requirement-to-test traceability plan;
- project risk/authority profile.
