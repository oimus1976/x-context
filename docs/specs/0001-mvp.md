# SPEC-0001 — x-context MVP

- **Status:** Proposed
- **Date recorded:** 2026-09-09
- **Related:** Issue #1, SPEC-0000, Review-0001, Review-0002
- **Scope:** Specification only; no product implementation in this work item

## 1. Purpose

x-context provides a read-only, official-API-based way to obtain X content for local tooling and AI-assisted analysis without relying on browser scraping, internal GraphQL endpoints, or cookie automation.

This specification defines the **P0 implementation slice** of the broader product direction described in `docs/specs/0000-product-scope.md`. Capabilities that are out of scope here may remain valid product candidates; they are not authorized for implementation until separately specified.

The MVP establishes three use cases:

- **UC-001:** Read an arbitrary X post from a supported status URL.
- **UC-002:** Read the authenticated user's bookmarks.
- **UC-003:** Read the authenticated user's liked posts.

Likes are included in P0 as a second authenticated activity collection so the first implementation can validate the canonical model and privacy boundary across more than one owned/read-only collection. This prioritization may be revisited before FR-004 implementation without changing the product-level read-only direction.

## 2. Design principles

1. The official X API is the only runtime data-access provider in the MVP.
2. Authentication scopes are read-only.
3. Credentials and private activity data are handled as sensitive local data.
4. JSON is the canonical machine-readable output contract.
5. Failure is explicit. Unsupported or unauthorized conditions do not trigger unofficial fallback behavior.
6. Material behavior changes follow: requirement -> acceptance criteria -> test -> implementation.
7. Billable/network work is bounded by default; P0 commands do not silently fetch an entire paginated collection.
8. Authenticated collection reads are subject-bound: P0 bookmarks/likes read only the currently authenticated user's own collection, not an arbitrary configured user ID.

## 3. Functional requirements

### FR-001 — Extract post ID from supported status URLs

The system shall extract a numeric post ID from supported X/Twitter status URLs.

#### Accepted URL families

- `https://x.com/{user}/status/{numeric_id}`
- `https://www.x.com/{user}/status/{numeric_id}`
- `https://twitter.com/{user}/status/{numeric_id}`
- `https://www.twitter.com/{user}/status/{numeric_id}`

Query strings and fragments may be present and must not alter the extracted status ID.

#### Acceptance criteria

- **AC-FR001-01:** A valid supported URL returns the exact numeric status ID.
- **AC-FR001-02:** Query parameters and fragments are ignored for ID extraction.
- **AC-FR001-03:** Non-X/Twitter hosts are rejected.
- **AC-FR001-04:** URLs without a numeric `/status/{id}` segment are rejected.
- **AC-FR001-05:** Rejection is explicit and does not make a network request.

### FR-002 — Fetch an arbitrary post through the official X API

Given a valid post ID, the system shall retrieve the post through the documented official X API.

#### Acceptance criteria

- **AC-FR002-01:** The request uses only the official X API provider implementation.
- **AC-FR002-02:** A successful response is normalized to the canonical output model.
- **AC-FR002-03:** Authentication and authorization failures are reported as explicit failures.
- **AC-FR002-04:** Unavailable-post conditions are reported distinctly from authentication failures.
- **AC-FR002-05:** Rate-limit conditions are reported distinctly and expose safe diagnostic metadata when available.
- **AC-FR002-06:** No failure path invokes scraping, browser automation, cookie access, or internal GraphQL.

### FR-003 — Fetch authenticated user's bookmarks

The system shall retrieve bookmarks for the **currently authenticated X user** using the official bookmarks endpoint available to that user's authorization context.

The implementation must derive or verify the authenticated subject identity using an official authenticated-user mechanism. If the provider endpoint requires a user ID path parameter, the supplied `{id}` must match the authenticated subject. P0 must not accept a caller-supplied arbitrary user ID for bookmark reads.

P0 bookmark retrieval is a **bounded one-page operation**. A command must not implicitly traverse every page. Continuation requires an explicit provider-issued page token supplied by the caller.

#### Acceptance criteria

- **AC-FR003-01:** The endpoint is called only with read-capable user authorization required by the official API.
- **AC-FR003-02:** Results are normalized to the canonical output model.
- **AC-FR003-03:** Pagination is represented explicitly; the implementation must not silently truncate while claiming completeness.
- **AC-FR003-04:** Bookmark payloads are not persisted by default.
- **AC-FR003-05:** Missing scope/permission is an explicit failure and does not trigger fallback access.
- **AC-FR003-06:** One CLI invocation retrieves at most one provider page; there is no implicit fetch-all behavior in P0.
- **AC-FR003-07:** If a continuation token exists, the output reports `page.complete = false` and returns that token; the caller may request the next page explicitly.
- **AC-FR003-08:** Requested page size is finite and defaults to 25 items. A caller may request a different positive size up to a product safety cap of 100; provider limits may reduce the effective request size but must not increase it beyond the caller/product cap.
- **AC-FR003-09:** The target user identity equals the authenticated subject identity before the bookmark collection request is made; a mismatch fails closed without issuing the collection request.
- **AC-FR003-10:** The CLI exposes no bookmark user-ID argument in P0.

### FR-005 — Canonical JSON output

The MVP shall expose one canonical normalized JSON model for successful reads.

Minimum top-level contract:

```json
{
  "schema_version": "1",
  "source": "x",
  "operation": "read|bookmarks|likes",
  "retrieved_at": "2026-09-09T10:00:00Z",
  "subject": null,
  "items": [],
  "page": {
    "next_token": null,
    "complete": true
  }
}
```

`retrieved_at` is the acquisition time for this envelope, expressed as an RFC 3339 UTC timestamp. It is distinct from a post's own `created_at`.

For authenticated collection operations (`bookmarks`, `likes`), `subject` identifies the authenticated X account whose collection was read. It must contain the authenticated X user ID and may include username when safely resolved. For arbitrary public post lookup (`read`), `subject` is `null`.

For collection operations, `page.complete` means **the returned page is known to exhaust the collection at that point**. It must be `false` whenever a continuation token is returned. It must not be used to imply historical completeness beyond what the provider response establishes.

Each item representing a post must support, when available from the official response and requested fields:

- post ID;
- text;
- author identity sufficient to represent X user ID and username when resolved;
- created-at timestamp when resolved;
- canonical X URL derived from normalized identifiers;
- referenced/quoted post metadata when included by the provider contract;
- media/link references when included by the provider contract.

Absence of an optional expansion must not be misrepresented as evidence that the underlying post has no such data.

#### Acceptance criteria

- **AC-FR005-01:** All three MVP operations use `schema_version = "1"`.
- **AC-FR005-02:** Output distinguishes absent/unrequested optional data from known-empty data where material.
- **AC-FR005-03:** Output contains no access token, refresh token, client secret, authorization header, cookie, or equivalent credential material.
- **AC-FR005-04:** Provider-specific response details do not become the public CLI contract unless explicitly specified.
- **AC-FR005-05:** Every successful envelope contains a valid UTC `retrieved_at` timestamp independent of post creation time.
- **AC-FR005-06:** `page.complete` is `false` whenever `next_token` is non-null; collection completeness is never inferred merely from a requested page-size boundary.
- **AC-FR005-07:** Successful bookmarks/likes output identifies the authenticated subject user ID; arbitrary `read` output uses `subject = null`.

### FR-006 — CLI contract

The MVP shall expose these logical commands:

```text
x-context read <x-status-url>
x-context bookmarks [--page-token <token>] [--max-results <n>]
x-context likes [--page-token <token>] [--max-results <n>]
```

For bookmarks/likes, omitted `--max-results` means 25. The accepted product range is 1 through 100. P0 intentionally has no `--all` or equivalent implicit multi-page command and no arbitrary target-user argument for authenticated collections.

The exact Python packaging/entry-point mechanism is an implementation decision, but the observable command behavior shall preserve this logical interface.

#### Acceptance criteria

- **AC-FR006-01:** Successful commands emit canonical JSON to standard output by default.
- **AC-FR006-02:** Human-readable diagnostics go to standard error and do not corrupt JSON output.
- **AC-FR006-03:** Failures produce a non-zero exit code.
- **AC-FR006-04:** Invalid local input is distinguishable from authentication, authorization, provider, rate-limit, usage-blocked, and unavailable-resource failures.
- **AC-FR006-05:** Normal command output does not include credentials or full authorization material.
- **AC-FR006-06:** `--page-token` is passed only to the selected collection operation and never causes automatic traversal beyond one page.
- **AC-FR006-07:** `--max-results` outside 1..100 is rejected locally before a network request.
- **AC-FR006-08:** `bookmarks` and `likes` expose no option or positional argument that changes the target away from the authenticated subject.

## 4. Non-functional and safety requirements

### NFR-001 — Official X API only

Runtime acquisition of X data in the MVP must use documented official X API interfaces only.

**Forbidden MVP fallback paths:**

- HTML scraping;
- browser automation;
- reuse of browser cookies;
- undocumented/internal GraphQL endpoints;
- third-party mirrors or scraping proxies presented as equivalent authority.

A future provider may be proposed only by changing this specification and the relevant ADR before implementation.

### NFR-002 — Read-only authorization boundary

The MVP must request only scopes/permissions needed for read operations. Write scopes for posting, deleting, liking, bookmarking, following, DM operations, or equivalent mutations are out of scope.

The implementation must not expose a write operation even if a supplied credential happens to possess broader authority.

Authenticated collection reads must also preserve a same-subject boundary: broader provider capability must not silently turn P0 into a reader for arbitrary users' activity collections.

### NFR-003 — Credential protection

Credentials must not be committed to Git, embedded in fixtures, emitted in logs, included in exception text intentionally, or written to normal command output.

Repository examples and tests must use obvious fake values.

### NFR-004 — Fail closed on unofficial fallback

If the official API cannot satisfy an operation, x-context must return an explicit error. It must not automatically switch to an unofficial acquisition path.

### NFR-005 — Usage/cost observability

The system **shall** expose enough non-secret diagnostic metadata to diagnose unexpected API consumption. At minimum, diagnostics must make the following observable per command execution without logging private payload bodies:

- operation name;
- number of provider requests attempted;
- returned item count;
- requested page size for collection operations;
- whether a continuation token was returned;
- safe provider rate/usage metadata when available.

The MVP must not compute or promise an exact monetary cost from hard-coded X prices. Pricing and Owned Read qualification are external platform facts and must be re-verified before any future exact-cost feature is specified.

Observability must not require logging private payload bodies or credentials.

### NFR-006 — Private activity data handling

Bookmarks and likes are treated as private user activity data even when the referenced posts are public.

Default behavior is process-and-return, not persist. Any future local persistence feature requires a specification change defining storage location, retention, deletion, and export behavior.

Subject identity needed to establish provenance may appear in canonical output, but private collection contents and opaque continuation tokens must not be copied into diagnostic logs by default.

## 5. Error model

The implementation must provide stable error categories sufficient for callers/tests to distinguish at least:

- `invalid_input`
- `authentication_failed`
- `authorization_failed`
- `subject_mismatch`
- `resource_unavailable`
- `rate_limited`
- `usage_blocked`
- `provider_error`
- `configuration_error`

`subject_mismatch` represents refusal to issue an authenticated collection request because the target user identity cannot be established as the currently authenticated subject.

`usage_blocked` represents provider refusal due to a usage, credit, spending, billing-cycle, or similar consumption gate when that cause can be established safely. It is distinct from short-window request throttling (`rate_limited`).

Provider-specific status codes and safe cause metadata may be recorded diagnostically, but callers must not need to parse arbitrary provider text to determine the stable category.

## 6. Security and privacy boundary

The MVP can read public posts by ID and the currently authenticated user's own bookmark/like activity permitted by the credential. It has no product-level mutation authority and no P0 authority to target arbitrary users' activity collections.

The following data must be considered sensitive in logs/tests/reports:

- access tokens, refresh tokens, client credentials;
- authorization headers;
- authenticated bookmark/like collections;
- opaque continuation/page tokens;
- raw private provider responses that include user activity not needed for a test artifact.

Real-boundary smoke evidence should record success/failure metadata and authenticated subject identity only to the minimum degree needed for provenance, without publishing private payload contents.

## 7. Out of scope for SPEC-0001

The following capabilities are excluded from this implementation slice. Some remain product-level candidates in SPEC-0000 and therefore must not be interpreted as rejected merely because they are not P0.

- posting, deleting, liking, bookmarking, following, blocking, muting, or any other X write operation;
- direct-message access;
- arbitrary-user bookmark/like collection targeting;
- mentions, lists, followers/following synchronization;
- background monitoring or scheduled ingestion;
- implicit fetch-all pagination or background crawl behavior;
- Obsidian/Markdown export;
- LLM summarization, classification, or enrichment;
- unofficial GraphQL, browser-cookie, scraping, or mirror providers;
- long-term persistence of X activity data.

## 8. Traceability contract

Every requirement implemented under this specification must have a corresponding acceptance-test mapping in `docs/TEST_MATRIX.md`.

A material behavioral change follows this order:

1. update the requirement/acceptance criteria;
2. update the test matrix and tests;
3. update implementation;
4. record validation evidence.

Implementation-first changes that are later backfilled into the specification are not the normal development path.

## 9. MVP implementation gate

Product implementation may begin only after the spec PR establishes:

- accepted MVP scope and its relationship to SPEC-0000;
- accepted provider/authentication boundaries;
- accepted same-subject identity boundary for authenticated collections;
- accepted bounded-pagination/usage behavior;
- accepted canonical output/error contracts;
- requirement-to-test traceability plan;
- project risk/authority profile.
